# 踩坑记录

工程实施中真实遇到并解决的问题。按「现象 → 排查 → 根因 → 处置」记录，供后来者少走弯路。

---

## 1. Cookie 不落盘，重启即失效

**现象**：登录成功，`Login state result: True`，但进程重启后变回访客。

**排查**：打开 `browser_data/*/Default/Cookies`（SQLite）查看，`web_session` 的 `expires_utc` 为 0——说明写成了会话 cookie。

**根因**：`login_by_cookies` 只写 `web_session` 一个键，且未设置 `expires`。Playwright 将其视为会话 cookie，上下文关闭即清除。

**处置**：遍历全部 cookie 并统一补 30 天过期时间。修复后 `web_session` 过期时间为 30 天后，清空 `COOKIES` 变量重跑仍通过登录校验。

## 2. 40 条任务 2 秒内全部发出

**现象**：设置的 `MAX_CONCURRENCY_NUM = 1`，实际却瞬间发出整批请求，随即触发 `300013`。

**排查**：在 `get_specified_notes` 里打点，发现 `asyncio.Semaphore(...)` 写在 `for` 循环**内部**，每条任务各建一个，限流形同虚设。

**根因**：上游实现缺陷。

**处置**：信号量提到循环外共享。修复后单条间隔稳定在 6 秒。

---

## 3. 进程被杀，整批 39 条数据消失

**现象**：采到第 39 条时进程被回收，重启后这批数据全是空的，但日志显示每条都抓成功了。

**根因**：`await asyncio.gather(*tasks)` 之后才统一 `set` 写入存储。数据全在内存里，进程一死全丢。

**处置**：改为每条完成后立即 `update_xhs_note`。代价是写入次数变多，收益是断点续跑绝对可靠。

沙箱平均每 20 分钟回收一次进程，这个改动是必须的。

## 4. 40 条被误记为「采集失败」

**现象**：某批次 40 条全部进入 `detail_failed.json`，后续批次全部跳过，形成 40 条假性缺口。

**排查**：那批的日志显示 Chrome 根本没启动成功，是基础设施故障，不是笔记问题。

**根因**：失败台账不区分「业务失败」与「基础设施失败」。

**处置**：只有明确的业务错误码（`-510001` / `-510000` Note not found）才记账；零产出且无业务错误码的，视为基础设施异常，不记账，下次重试。

## 5. SingletonLock 残留导致 Chrome 拒绝启动

**现象**：进程启动即退出，无报错，零产出。

**根因**：上次进程被强杀，`browser_data/cdp_xhs_user_data_dir/SingletonLock`（符号链接）残留，Chrome 认为已有实例在跑。

**处置**：每轮启动前 `rm -f .../Singleton*`，并 `pkill -9 -x chrome` 清理僵尸进程。写进 `supervise.sh` 后此类故障不再出现。

## 6. Playwright 报找不到 chromium-1228

**现象**：`Executable doesn't exist at .../chromium-1228/chrome-linux/chrome`。

**根因**：Playwright 1.58 期望 chromium-1228，本机装的是 Chrome for Testing 145（对应 1208 目录）。

**处置**：软链接补齐：

```bash
ln -s chromium-1208 chromium-1228
ln -s chromium_headless_shell-1208 chromium_headless_shell-1228
```

因为是 CDP 模式连接系统 Chrome，实际不依赖这份二进制，补链接只是为了让 Playwright 的路径检查通过。

## 7. pkill 把自己的进程杀了

**现象**：执行 `pkill -f run_daemon.sh` 后，下这条命令的 shell 也退出了，任务状态变成 failed。

**根因**：`pkill -f` 匹配完整命令行，而当前这条命令的命令行里就包含 `run_daemon.sh` 这个字符串——自匹配。

**处置**：用方括号破坏字面匹配：

```bash
pkill -f "run_[d]aemon.sh"      # 不会匹配到自身
pkill -f "run_xhs_[d]etail"
```

## 8. 定时任务「执行了」但什么都没发生

**现象**：用自动化调度建了每小时巡检任务，`lastRunAt` 有值，但目标文件不存在、日志无痕迹。

**排查**：建一次性探针任务，让它写一个文件到 `/workspace`。任务状态显示已执行，`/workspace` 下却没有该文件。

**根因**：自动化任务跑在**独立容器**里，与采集所在的容器不共享文件系统。巡检脚本看不到采集进程，自然也无法告警。

**处置**：放弃跨容器巡检，改为**采集端自愈**——守护脚本在采集容器内自行判断零产出、重建环境、熔断停机，所有状态写入日志。需要人看的时候，直接读日志。

**教训**：在分布式/容器化环境里，「定时任务」不等于「能在同一个现场跑」。先验证文件系统和进程可见性，再设计巡检。

## 9. 容器空闲回收被误判为脚本崩溃

**现象**：日志停在正常写入的一行，没有 traceback，没有退出码，进程消失。

**排查**：对比多次发生的时间点，发现间隔不固定（7 分钟、20 分钟），且**所有进程同时消失**——包括采集、Xvfb、以及后台监控任务本身，连任务记录都查不到。

**根因**：沙箱的空闲回收机制，与脚本无关。

**处置**：长任务期间保持一个前台命令在跑（如 `sleep` 循环），显著延长存活时间；同时依靠逐条落盘保证断点可靠。本项目实测从平均 7-20 分钟被回收，延长到连续 3 小时无中断。

**判别方法**：看是否**所有进程同时消失**。只有一个进程死是脚本问题，全部同时死是外部回收。

## 10. 短信登录死在二次验证

**现象**：手机号 + 验证码流程走完，页面跳转 `Scan to verify`。

**排查**：先是发现「获取验证码」按钮点不到——点击落到了外层容器 `div` 上，短信根本没发出。改成遍历 `button,span,div,a` 找含「验证码 / 重新发送」文本的元素后才发出。但验证码提交后仍然进入扫码验证。

**结论**：小红书对短信登录路径有额外风控，纯自动化走不通。改用 Cookie 直填。

**教训**：不要在登录环节死磕。Cookie 注入是成本最低、最稳定的方案，只要能拿到一次登录态。

## 11. 详情 API 报 300013，但 HTML 能打开

**现象**：`v1/feed` 返回 `error_code: 300013 访问频繁`，同时 `curl` 直接请求笔记页返回 200。

**排查**：四种组合对照——无 Cookie、有 Cookie、裸 Playwright、完整反检测配置，全部被拦。`curl` 拿到的 HTML 是空壳，正文走的是 SSR 注入的 `__INITIAL_STATE__`，页面本身不调 feed 接口。

**结论**：限流发生在内容 API 层，与浏览器指纹、Cookie 状态无关，根因是数据中心出口 IP。同 IP 下换什么配置都没用。

**处置**：控制请求节奏（6 秒/条），识别到 `300013` 指数退避；识别到 `HTTP 461` 立即停止 12-24 小时。要彻底解决只能换住宅 IP。

## 12. 免登录详情的边界

**验证结论**：

| 能力 | 游客可用 | 说明 |
|---|---|---|
| 笔记页正文 | ✅ | SSR 注入 `__INITIAL_STATE__`，DOM 可解析 |
| 评论区列表 | ✅ | `v2/comment/page` 返回 200，实测 23-30 条 |
| 内容详情 API | ❌ | `v1/feed` 返回 `code: -101 无登录信息` |

所以「免登录采集」在 DOM 层面可行，但拿不到完整评论分页与互动数据，且不稳定。生产环境仍走登录 + API。

## 13. 自动化任务与采集进程互踢

**现象**：多个 MCP 实例同时操作同一账号，登录态反复失效。

**根因**：小红书同账号多会话互踢。

**处置**：废弃多实例方案，全局串行。任何时刻只允许一个采集进程持有登录态。

## 14. 免 cookie 通道：iPhone UA 可打 SSR，但会软封（2026-11-02 实测）

**可用形态**

| 请求 | 结果 |
|---|---|
| 桌面 UA（Chrome/mac）`/explore/<id>?xsec_token=` | ❌ 302 → `/login` |
| headless Chrome 全新 profile（纯游客） | ❌ 落在登录页 |
| **iPhone UA** + `curl --noproxy '*' -L` + 带 token | ✅ 200，SSR 里 `noteData.data.noteData` 含 title/desc/user.nickName(tags)/imageList/interactInfo，另有 `commentData.comments`（一级+子评论） |

- 评论只有**首屏一页**（约 10 条一级 + 子评论）：commentCount=1200 的笔记只给 20 条；≤12 条时基本全给。
- `/api/sns/web/v1/feed`、`/api/sns/web/v2/comment/page` 无签名直连一律 `{"code":-1,"success":false}`。
- 一致性已验：20 条与登录态采集结果比对，正文前缀 20/20 一致，点赞/评论数 12 条完全相等、8 条差 1–5（快照时间差）。

**失效形态**

`200` + 约 23KB 壳页，可见文案「当前内容仅支持在小红书 APP 内查看」。
两种原因会得到同一个壳页：① URL 缺 `xsec_token`（案例库 217 条中有 37 条缺）；② **被降级**。
判别要靠上下文，不能一律当笔记已删。

**限流特征**

- 连续约 50–60 次后**全局降级**：连 10 分钟前成功抓过的笔记也返回壳页；间隔 16 秒改善不了。
- 补匿名 cookie（abRequestId/acw_tc）、换出口 IP（实测新加坡节点）**均无效** → 匿名指纹级累计风控，不是单纯 IP 限频。
- 处置建议：单轮 ≤40 条、间隔 ≥3s、连续 3 条空即熔断停 30–60 分钟；长任务拆多轮。冷却时长仍待观测。
