# 采集方法

本文记录从小红书获取二奢回收负面案例的完整方法，包括环境搭建、登录、限流策略、断点续传与风控处置。

---

## 一、技术栈

| 组件 | 版本 | 用途 |
|---|---|---|
| Python | 3.11 | 运行环境（uv 管理） |
| MediaCrawler | 上游主干 | 平台适配层、签名、存储 |
| Playwright | 1.58 | 浏览器驱动 |
| Chrome | 144 / Chrome for Testing 145 | 真实浏览器（CDP 模式） |
| Xvfb | :99 | 无头环境的虚拟显示 |
| xhshow | - | 小红书 `x-s` / `x-t` 请求签名 |

选 MediaCrawler 而非自建，是因为它已经实现了小红书登录态维护、`x-s` 签名、异步并发框架。但**默认配置不能直接用于本场景**，需要三处修复，见第五节。

---

## 二、登录

小红书登录有三条路径，实测只有一条可用：

| 路径 | 结果 | 原因 |
|---|---|---|
| 短信验证码 | ❌ | 提交验证码后触发 `Scan to verify` 二次安全验证，纯短信走不通 |
| 扫码 | ⚠️ | 可行但脆弱：二维码 60 秒自动刷新，MCP 会话被后续请求重置时旧码立即失效 |
| **Cookie 直填** | ✅ | 浏览器登录后导出，最稳定 |

### Cookie 注入

从已登录的浏览器导出 cookie JSON 数组（EditThisCookie 格式，需含 `web_session`、`a1`、`webId`、`id_token`），写入 `~/.xiaohongshu/cookies.json`。

关键点：**`web_session` 必须带 `expires`**，否则作为会话 cookie 不落盘，进程重启即失效。上游 `login_by_cookies` 的处理有缺陷，见第五节「补丁 1」。

### 登录态校验

访客也会有 `web_session`（值不同），不能以此判断登录成功。可靠判据是页面登录框是否消失、URL 是否跳转。

## 三、浏览器模式

生产使用 **CDP 模式连接真实 Chrome**，而非 Playwright 自带的 Chromium：

```python
ENABLE_CDP_MODE = True
CUSTOM_BROWSER_PATH = "/usr/bin/google-chrome"
```

profile 落于 `browser_data/cdp_xhs_user_data_dir`。这样做的原因：

1. 真实 Chrome 指纹干净，`--disable-blink-features=AutomationControlled` 之外不需要额外反检测
2. profile 持久化，登录态、历史记录、localStorage 都保留
3. 后面补采时可以复用同一份 profile，免登录

注意：CDP 目录与 MediaCrawler 标准模式的 `xhs_user_data_dir` **不互通**，Cookie 不能互相复制，需要各自登录。

无头环境需要虚拟显示：

```bash
Xvfb :99 -screen 0 1440x900x24 -nolisten tcp &
export DISPLAY=:99
```

## 四、限流策略

### 风控信号分级

| 信号 | 含义 | 处置 |
|---|---|---|
| `error_code: 300013` 访问频繁 | 内容 API 层限流 | 指数退避，暂停 5-10 分钟 |
| `HTTP 461` | 明确的风控验证码挑战 | **立即停止**，冷却 12-24 小时 |
| `code: -510001 / -510000` Note not found | 笔记已删除/私密/下架 | 记入失败台账，不再重试 |
| `code: -101` 无登录信息 | 登录态失效 | 重新注入 Cookie |

`300013` 和 `461` 性质不同：前者是频率问题，降速可解；后者是风控判定，继续请求有封号风险。

### 参数设定

```bash
uv run python run_xhs_detail.py \
  --batch-size 40 \    # 每批条数
  --cooldown 90 \      # 批间冷却秒数
  --gap 6 \            # 单条间隔秒数
  --max-empty-rounds 2 # 连续零产出熔断阈值
```

实测吞吐约 **8.6-10.5 秒/条**（含评论抓取）。压到 3 秒间隔速度提升约 40%，但 `300013` 概率显著上升，不建议。

### 并发限制必须真的生效

上游在小红书详情采集里，为**每条任务**新建一个 `asyncio.Semaphore`，导致并发上限实际失效——40 条任务在 2 秒内全部发出，必被限流。修复见第五节「补丁 2」。

## 五、上游三处修复

MediaCrawler 原版在「长久运行 + 大批量补采」场景下有缺陷，本项目打了三个补丁。以下为改动说明，仓库不包含上游代码。

### 补丁 1：Cookie 落盘

`media_platform/xhs/login.py` → `login_by_cookies`

```python
# NOTE(local patch): 补 expires，否则会话 cookie 不落盘
expires = int(time.time()) + 30 * 24 * 3600
```

原实现只写 `web_session` 且不带过期时间，浏览器上下文关闭后登录态丢失。修复后 profile 中 `web_session` 过期时间为 30 天后，清空 `COOKIES` 变量重跑仍能通过 `Login state result: True`。

### 补丁 2：并发信号量

`media_platform/xhs/core.py` → `get_specified_notes`

```python
# NOTE(local patch): 循环外共享，否则每条任务各建一个，并发限制失效
detail_semaphore = asyncio.Semaphore(config.MAX_CONCURRENCY_NUM)
```

### 补丁 3：逐条落盘

`media_platform/xhs/core.py` → `get_specified_notes`

原实现 `await asyncio.gather(*tasks)` 后统一写入存储。进程在批次中途被杀，整批 39 条全部丢失（只保留内存中的）。改为每条完成后立即 `await xhs_store.update_xhs_note(note_detail)`。

代价是写入次数变多，收益是**断点续跑绝对可靠**——沙箱每天回收数次，这一点比吞吐量重要。

### 附加：匿名模式

`cmd_arg/arg.py` 增加 `NONE = "none"` 登录类型，`core.py` 在 `LOGIN_TYPE == "none"` 时跳过 `pong` 登录流程，用于验证「免登录能拿到什么」。

## 六、断点续传

`run_xhs_detail.py` 的三层跳过逻辑：

1. **已采跳过**：扫描 `data/xhs/jsonl/*contents*.jsonl` 全部 `note_id`，在候选池中剔除
2. **失败台账**：`detail_failed.json` 记录确定性失败（已下架），不重复请求
3. **逐条落盘**：单条完成即写盘，被杀只丢当前这一条

关键设计：**基础设施异常导致的零产出不记失败台账**。之前因为 Chrome 启动失败，40 条被打上「失败」标记，后续批次全部跳过，造成假性缺口。现在只有明确的业务错误（`-510001`）才入台账。

## 七、守护与自愈

`supervise.sh` 每轮启动前执行：

```bash
rm -f browser_data/cdp_xhs_user_data_dir/Singleton*   # Chrome 锁残留
pkill -9 -x chrome                                     # 僵尸进程
pgrep -f "Xvfb :99" || Xvfb :99 -screen 0 1440x900x24 & # 重建显示
```

`SingletonLock` 是高频坑：进程被强杀后锁文件残留，下次启动 Chrome 直接拒绝并退出，表现为「零产出」。每轮必清。

熔断：连续 2 轮零产出即停，判定为风控，等待人工介入，不硬刷。

### 沙箱环境的一个陷阱

进程在无前台任务时会被容器回收，日志停在正常写入的一行、没有 traceback、没有异常退出码。判断方法是看**是否所有进程同时消失**（采集、Xvfb、后台监控全没），是则属于外部回收而非脚本故障。

应对：长任务期间保持一个前台命令在跑（例如 `sleep 570` 循环），可显著延长存活时间。本项目实测从平均 7-20 分钟被回收，延长到连续 3 小时无中断。

## 八、数据字段

每条笔记采集后落盘为 JSONL：

| 字段 | 说明 |
|---|---|
| `note_id` | 笔记 ID |
| `title` / `desc` | 标题 / 正文 |
| `author` | 作者昵称 |
| `liked` / `collected` / `comment_count` | 互动数 |
| `url` | 原文链接 |
| `publish_ts` | 发布时间戳 |
| `source_keyword` | 召回的搜索词（补采来源） |

评论单独落盘：`detail_comments_*.jsonl`，字段含 `note_id`、`content`、`like_count`、`sub_comments`。

## 九、抓取节奏复盘

| 轮次 | 目的 | 关键词 | 产出 | 风控 |
|---|---|---|---|---|
| 1 | 宽泛召回 | 二奢/回收/平台名（组合） | 944 候选 | 无 |
| 2 | 详情补采 | - | 697 条正文 + 3,915 评论 | 早期并发 bug 触发过 300013，修复后无 |
| 3 | 负面词补搜（双平台） | 12 个 | 239 条，净增 143 | 无 |
| 4 | 转转专项 | 8 个 | 第 4 个词触发 461，主动停止 | **有** |

第四轮的 461 说明：连续三天高频采集后，风控阈值会下降。此时应换 IP 或等冷却，而不是换关键词继续试。

## 十、可复现性说明

本项目**不包含**：

- Cookie / 登录凭据（涉及账号安全）
- MediaCrawler 上游代码（遵循其仓库许可，仅以补丁说明形式记录改动）
- 原始 HTML 与浏览器 profile

复现需要：自备小红书账号、自备可用的出口 IP、按本文档打三个补丁。采集量、时间窗口不同，结果会有差异，但方法链路一致。
